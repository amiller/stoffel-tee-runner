### report_data[8..40] quote binding — pod-only claim, pinned by tests
# A fresh hardware quote binding blake3(pubkey) at [8..40] (with [0..8] still
# the LE tls_derived_id) can only be minted inside a TDX CVM; zed has none and
# the pod deploy needs operator credentials, so it is NOT claimed here. What is
# pinned in the fork's test suite (cargo test -p stoffel-vm attestation, both
# feature sets):
#   - report_data layout: [0..8] LE tls id, [8..40] blake3(pubkey), [40..64] zero
#   - verify_dstack_quote_with_registers extracts [8..40] as the node-key binding
#   - the vendored REAL Intel TDX quote (minted pre-L1 by a pre-0.4 dstack whose
#     report_data is a hash of the request, so [8..40] is non-zero digest bytes)
#     is now REFUSED with MissingNodePubKey — the honest L1 outcome for a quote
#     that binds bytes at [8..40] while presenting no pubkey
#   - mock-level: binding match ADMITS, mismatch → PubKeyBindingMismatch,
#     tampering the binding breaks the quote MAC
#
# Pod caveat for the re-run: if the pod's dstack predates verbatim report_data
# (pre-0.4), an L1 node's binding at [8..40] would be overwritten by the
# platform and admission would fail LOUDLY (PubKeyBindingMismatch) — not
# silently. The w7 pod's August runs prove its dstack passes [0..8] verbatim
# (four parties admitted with report_data[0..8] == their real tls_derived_id),
# so [8..40] is expected to pass through the same way; verify on the re-run.
